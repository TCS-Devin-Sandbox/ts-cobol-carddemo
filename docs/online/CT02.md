# E9 — CT02 transaction add

Sources: `app/cbl/COTRN02C.cbl`, `app/bms/COTRN02.bms`,
`app/cpy-bms/COTRN02.CPY`, `app/cpy/CVTRA05Y.cpy`, `CVACT03Y.cpy`,
and `app/cbl/CSUTLDTC.cbl`. No customer estate or golden files changed.

## Contract and preserved behavior

Authenticated USER and ADMIN sessions use `POST /api/transactions/add`.
JSON fields use the existing transaction table's business column names plus
`account_id` and `confirmation`. The response contains `fields`, `message`,
`field` (cursor target), and `added`. Errors redisplay with HTTP 200 like E6.
Main-menu option 8 routes to `/transactions/add`; the screen uses the existing
JWT, header, message and function-key components. No new database migration.

* Account ID has priority when both keys are supplied, even if the card is
  invalid. It must occupy eleven numeric positions; card-only input must
  occupy sixteen. CXACAIX becomes a card_xref lookup ordered by card key;
  when multiple cards share an account, the first card wins. The resolved
  other key replaces the entered value. No account, customer or active-card
  check is added: those are not performed here in the legacy program.
* Key validation precedes data validation. Missing data is checked in source
  EVALUATE order: type, category, source, description, amount, origination,
  processing, merchant ID/name/city/ZIP. All empty and numeric messages retain
  capitalization and punctuation. Type/category/merchant ID require exactly
  2/4/9 digits, not membership in a code table. ZIP is only required.
* Amount requires an explicit sign, eight integer digits, decimal point and
  two fractional digits (`-99999999.99` or `+99999999.99`). Zero is normalized
  positive by the NUMVAL-C/display move. Numeric/date format checks precede
  calendar checks, and merchant numeric validation comes last.
* Dates are ten-character YYYY-MM-DD strings, not timestamps generated from
  the server clock. CSUTLDTC calls CEEDAYS; invalid calendar dates and year
  zero are rejected. Its nonzero result 2513 (unsupported range) is expressly
  ignored by CT02, so valid dates before 1601 are allowed. No past/future or
  origin-versus-processing ordering rule is invented. Stored CHAR(26) dates
  contain the ten input characters followed by spaces, just like the MOVE.
* Blank/N/n confirmation always asks `Confirm to add this transaction...`;
  other values except Y/y show `Invalid value. Valid values are (Y/N)...`.
  Y/y inserts after the same validation. This is not a server-side tokenized
  approval: changing fields and supplying Y in one request is allowed, as in
  the terminal. Failed validation does not consume an ID.
* The ID is the lexically last TRANSACT key plus one, zero-filled to sixteen
  positions, with PIC overflow wrapping. It is not count+1, a sequence or a
  per-account counter. Empty READPREV starts at zero. Concurrent inserts can
  collide: the duplicate response remains `Tran ID already exist...`; no
  silent retry or changed identifier allocation is introduced.
* PF5 resolves the key first, then copies the **global** last transaction,
  not the account's last transaction. It does not copy card, ID or confirmation.
  The source's narrow BMS moves truncate description/name/city to 60/30/25,
  category/merchant retain zeroes, dates retain their first ten positions,
  and amount loses an overflowing ninth integer digit. It then executes the
  normal Enter flow; an existing Y confirmation can therefore immediately
  insert the copied transaction. Empty copy redisplays initialized record
  values (blank text, numeric zeroes) and fails the required type edit.
* Success clears all fields/confirmation, returns focus to account, and uses
  the exact success message including the sixteen-position new ID. PF4 clears
  fields and message without any request. PF3 returns to the caller when
  supplied in route state, otherwise the main menu. Optional route state
  `cardNumber` replaces the legacy selected-key COMMAREA field (despite that
  field's misleading transaction-selected name); initial entry validates it.
* Missing JWT replaces EIBCALEN=0/sign-on XCTL. HTTP replaces pseudo-conversation,
  SELECT replaces STARTBR/READPREV/ENDBR, controlled fields replace RECEIVE/SEND,
  and cursor/color are focus plus error/success message styling. The unused
  ACCTDAT copy/constant, USR-MODIFIED flag and CT02 paging fields add no rules.

## HTTP boundary distinctions

BMS physically prevents oversized fields. The UI enforces the same lengths;
direct API callers receive a width error rather than silent HTTP truncation.
SQL has no separate STARTBR NOTFND response when seeking high-values: an empty
result implements READPREV ENDFILE. Other lookup/write failures preserve the
source messages without returning database exception details. There is no
persistent browse cursor or lock across HTTP requests. A failed key returns
immediately from SEND/RETURN in the source, so the later ERR-FLG clearing block
in VALIDATE-INPUT-DATA-FIELDS is unreachable for those key errors.

## Runnable C2 acceptance

Start the local Compose PostgreSQL and dev API as documented in AGENTS.md.
Then, from the repository root, with JDK 21 and Docker:

```sh
CT02_ACCEPTANCE=true mvn -B -f java/pom.xml -pl posting -am \
  -Dtest=OnlineTransactionAcceptanceTest -Dsurefire.failIfNoSpecifiedTests=false test
```

This opt-in local-only test adds the synthetic fixture xref to the local dev DB
if absent, signs in over HTTP, requests confirmation, inserts over HTTP, reads
the stored row over HTTP, and encodes it using java/common's CVTRA06Y codec.
It runs the actual C2 PostingCandidate with matching p01 account/xref fixtures
in an isolated Testcontainers PostgreSQL database, asserting STEP15 RC 0, empty
rejects and one TRANSACT row with the API's ID. It does not mock the posting
store or replace the created transaction with a handwritten daily record.
It leaves the synthetic online row/xref available for browser verification;
it never runs against shared/production services. This demonstrates record
compatibility, not a production queue/cutover scheduler. As in C2, posting
opens TRANSACT for OUTPUT in the isolated batch schema and replaces proc time.
