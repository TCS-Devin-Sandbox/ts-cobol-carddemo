# E10 — CB00 bill payment

[COBIL00C](../../app/cbl/COBIL00C.cbl) sends and receives
[COBIL0A in COBIL00](../../app/bms/COBIL00.bms). CM00 option 10 opens
`/bill-pay`; F3 returns to CM00 and F4 clears the map. The first screen
has an empty, focused account ID. Enter posts the map; other function keys
show `Invalid key pressed. Please see below...` and keep the input.

## Data and HTTP contract

Authenticated operators (USER or ADMIN) post
`{"accountId":"00000000042","confirm":"","currentBalance":null}` to
`/api/bill-payments`. `currentBalance` is the balance the browser shows:
CURBAL is an FSET field, so the legacy map sends it back and redisplays it
on paths that do not read the account. The API echoes it and never uses it.

The HTTP 200 response is the redraw:
`{accountId, currentBalance, confirm, message, severity, focus, transactionId}`.
`severity` is `error` (red ERRMSG, including the confirmation prompt) or
`success` (DFHGREEN). `focus` names the field that gets the cursor (`MOVE -1`).
Authentication failure returns 401. A database outage before the unit of work
starts returns 503 and the generic `Unable to lookup Account...`.
Responses are `Cache-Control: no-store`. The browser shows the balance in the
WS-CURR-BAL picture `+9999999999.99`.

| Step | CICS file / copybook | PostgreSQL behavior |
|---|---|---|
| READ-ACCTDAT-FILE | ACCTDAT / CVACT01Y, READ UPDATE | `SELECT … FOR UPDATE` on `account`. The lock waits for `carddemo.db.lock-timeout`, then takes WHEN OTHER. |
| READ-CXACAIX-FILE | CXACAIX / CVACT03Y | First `card_xref.card_number` for the account, in key order. |
| STARTBR / READPREV / ENDBR | TRANSACT / CVTRA05Y | The highest `transaction_id` (C collation) plus 1, wrapping at 10^16 like `ADD 1` to `9(16)`. An empty table gives `0000000000000001` (the ENDFILE branch). A transaction-scoped advisory lock serializes concurrent payments. |
| WRITE-TRANSACT-FILE | TRANSACT / CVTRA05Y | Inserts type `02`, category `2`, source `POS TERM`, `BILL PAYMENT - ONLINE`, amount = current balance, the card from step 2, merchant `999999999` / `BILL PAYMENT` / `N/A` / `N/A`, origination = processed = `YYYY-MM-DD HH:MM:SS.000000` server local time. |
| UPDATE-ACCTDAT-FILE | ACCTDAT / CVACT01Y, REWRITE | `current_balance - amount`. The cycle credit and debit are not changed. |

Steps 1–5 run in one PostgreSQL transaction. Column-to-copybook mappings are in
[the shared VSAM schema guide](../schema-mapping-vsam.md).

## Preserved behavior and deviations

* An empty account ID is checked first; the confirmation value is ignored.
  `N`/`n` clears the screen without reading the account (unknown IDs too).
  Any other nonblank value gives `Invalid value. Valid values are (Y/N)...`
  without reading the account.
* ACTIDIN is X(11) moved to ACCT-ID 9(11) with no numeric edit, so a value that
  is not exactly 11 digits matches no key: `Account ID NOT found...`.
* The balance is read and shown even when the payment is not confirmed. Zero or
  credit balances give `You have nothing to pay...`; a blank confirmation gives
  `Confirm to make a bill payment...` with the cursor on CONFIRM.
* Success shows `Payment successful.  Your Transaction ID is <id>.` (two spaces,
  from the STRING) and clears every field, as INITIALIZE-ALL-FIELDS does.
* CXACAIX is a non-unique path. For an account with several cards, READ returns
  the first card with DUPKEY. The legacy message is overwritten by the success
  message and the payment goes through, so the API uses the lowest card number.
* **Deviation:** The legacy program does not stop on errors after the account
  read. After a cross-reference miss or a TRANSACT browse or WRITE failure, it
  still runs REWRITE, which can zero the balance without a transaction record.
  When REWRITE fails, it keeps the written transaction. The port stops at the
  first failure, shows that paragraph's message, and rolls back both writes:
  * XREF not found: `Account ID NOT found...`
  * Non-numeric last key: `Unable to lookup Transaction...`
  * DUPREC: `Tran ID already exist...`
  * Other write failure: `Unable to Add Bill pay Transaction...`
  * Rewrite failure: `Unable to Update Account...`
* `CDEMO-CB00-TRN-SELECTED` pre-fills the account on first entry, but no program
  in the estate sets it (only COBIL00C and the CSD name CB00), so there is no web
  equivalent. The header uses the shared browser date and time.

## Consistency with C2 (POSTTRAN / CBTRN02C)

`BillPayPostingConsistencyTest` pays a balance of 250.00 through the API. It
then runs the real C2 jar (`java/posting/target/carddemo-posting.jar --chain
posting`) on records encoded with the CVACT01Y / CVTRA06Y layouts:

1. C2 loads the account record that CB00 leaves behind and posts the next day's
   40.00 purchase from it. The balance is 40.00, and the cycle credit/debit
   are the pre-payment values plus the purchase.
2. C2 posts the same payment from the pre-payment account as a credit
   (-250.00, type 02 / category 2). It reaches CB00's balance, 0.00.
3. Legacy sign quirk: CB00 writes TRAN-AMT as the positive balance and subtracts
   it. C2 adds DALYTRAN-AMT. If C2 replays CB00's TRANSACT row unchanged, the
   balance becomes 500.00. C2 also books the credit to `current_cycle_debit`
   and `transaction_category_balance`, which CB00 does not change. Both are
   legacy behavior and are not changed here.

The test is skipped when the jar is not built. CI builds it before the online API tests.
