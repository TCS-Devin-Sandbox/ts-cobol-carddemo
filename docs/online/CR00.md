# CR00 — Transaction Reports

Main Menu (CM00) option **09** opens CR00 for a signed-in user. CR00
replaces the JOBS transient-data queue and JES internal reader with a call to
the Java posting launcher. It does not run POSTTRAN or update online master
tables, display a report, or connect to a printer.

## Running and operating

Build the launcher with Java 21 from the repository root:

```sh
mvn -B -f java/pom.xml -pl posting -am package
```

Start the online API as usual, with the shared VSAM tables in the default
PostgreSQL `public` schema. The configured DB login needs read access to
`transaction`, `card_xref`, `tran_type` and `tran_category` there and permission
to create/drop the launcher's own scratch schemas. Point the API at the
installed jar if running outside the source tree.

| API property | Default (working directory: online API) |
|---|---|
| `carddemo.reports.posting-jar` | `../java/posting/target/carddemo-posting.jar` |
| `carddemo.reports.java` | `java` (Java 21 on PATH) |
| `carddemo.reports.output` | `../work/reports` |

For a confirmed request, the API starts one child process and returns its
report ID without waiting for completion. Only one process may run per API
instance; retry after the active report finishes if the launcher is busy.
Use an access-restricted, persistent output directory in deployed environments;
each ID has its own `launcher.log`, datasets, report SYSOUT, and (on completion)
`rc.json`. The artifacts can contain card data and are not served by the API.
Operators manage retention and inspect failures; there is no durable queue or
automatic re-submit in this port.

The launcher snapshots the already-posted rows and report reference data in a
scratch schema and drops it after the run. The full posting parity command
still uses its own fixture database inputs, including its separate SORT and
DATEPARM ranges.

## Legacy choices

- A marked monthly choice wins over yearly, which wins over custom, as in
  COBOL. The browser uses checkboxes instead of one-character markers.
- The server's local date supplies month/year. Date fields zero-pad digits
  instead of implementing all of `NUMVAL-C`'s currency/sign syntax. Calendar
  validity uses proleptic Gregorian dates rather than calling z/OS CEEDAYS;
  valid earlier dates are not rejected solely for being outside CEEDAYS' range
  (legacy code ignores feedback 2513). No new end-before-start check: an
  inverted range matches no transactions.
- A successful response acknowledges submission, not rendering or printing.
  A failure to start the process replaces the legacy TDQ write error. A later
  step failure is recorded by the batch process, not shown as a form error.
